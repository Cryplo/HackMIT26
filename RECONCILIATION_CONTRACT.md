# Reimbursement MVP: shared implementation contract

Build a hackathon travel reimbursement demo in `reconciliation/`. Preserve the existing browser prototype. Three independent tasks own intake, core, and dashboard. Do not expand scope into payments, authentication, DOCX, browser integration, or blind re-run auditing. Use synthetic demo data and USD only. Unknown receipt values are null, never inferred zeroes. No real financial or bank details.

## Stack and ownership

One Next.js App Router TypeScript app, React, Tailwind, Zod, Supabase Postgres/private storage. Choose compatible pinned versions and document them. Module 1 owns project scaffold/package manifest/lockfile, root layout/styles, `/submit`, `/api/submissions`, `/api/receipts`, and `src/lib/intake/**`. Module 2 owns `src/lib/core/**`, `src/app/api/reconcile/**`, `src/app/api/corrections/**`, `src/app/api/reviews/**`, `supabase/**`, and `src/lib/contracts.ts`. Module 3 owns `src/app/business-demo/**`, `src/components/business/**`, and `src/lib/dashboard/**`. Do not modify another module's files; document needed dependency changes in a module handoff file. Prefer native tables and CSS over requiring extra dashboard libraries. Each module may add its own tests and fixtures under its owned directories.

## Tables (snake_case)

- submissions: id uuid, attendee_name text, email text, amount_requested_minor integer >= 0, currency USD, category flight|hotel|train|bus|other, origin_location text, submitted_at timestamptz, updated_at timestamptz, status pending|approved|flagged|needs_review|rejected, latest_run_id nullable uuid.
- receipts: id uuid, submission_id uuid FK, storage_path text, file_type text, raw_extracted_text nullable text, parsed_fields_json nullable jsonb, extraction_status pending|succeeded|failed, extraction_error nullable text, extracted_at nullable timestamptz.
- policy_rules: id uuid, category, region_or_route text (MVP `*` catch-all), currency USD, max_amount_minor integer, date_range_start date, date_range_end date, created_at timestamptz. Require exactly one applicable policy; missing/ambiguous policy -> needs_review.
- reconciliation_runs: id uuid, submission_id uuid FK, status running|completed|failed, started_at, completed_at nullable, error nullable. Publish latest_run_id and submission status only when all decisions are saved, atomically. Prevent duplicate active runs for a submission.
- decisions: id uuid, run_id uuid FK, submission_id uuid FK, field_checked text, check_method deterministic|jev|human, question_type boolean|choice|score|rule, answer_json jsonb, probability nullable float, confidence_score nullable float, verdict pass|fail|unknown, rationale_text text, evidence_json jsonb, state_snapshot_json jsonb, model_used nullable text, created_at. Include an overall_status decision; answer_json is {value: ...}. Never confuse probability of true with confidence. Log actual provider response separately in evidence if useful.
- corrections: id uuid, submission_id uuid FK, decision_id nullable uuid FK, human_verdict approved|rejected, human_note text, correction_type decision_override|vendor_alias, correction_payload_json jsonb, corrected_at. Alias payload {observed_vendor, canonical_vendor, scope:{category,currency}}. A decision_override is one-time and never reusable policy. Module 2 consumes applicable alias corrections on later runs.
- model_calls: id uuid, run_id nullable uuid, receipt_id nullable uuid, provider, model, input_tokens nullable integer, output_tokens nullable integer, latency_ms integer, estimated_cost_usd nullable numeric, created_at. Count usage once per API call; don't invent unavailable costs.

Receipt parsed_fields_json exact shape: {schema_version:1,vendor:string|null,receipt_date:string|null,amount_minor:integer|null,currency:string|null,names:string[],receipt_number:string|null}. Dates YYYY-MM-DD. MVP one receipt per submission; additional uploaded receipts may be rejected clearly. Amounts integer minor units throughout.

## APIs

All API errors: {error:{code:string,message:string}} with suitable HTTP status. Validate server-side. Server-only secrets. Same-origin mutation checks, upload limits, and private storage; demo remains unauthenticated and must be labeled synthetic-data-only. No public storage URLs or service-role keys in client code.

- POST /api/submissions multipart fields: attendee_name,email,amount_requested_minor,currency,category,origin_location,file. Module 1 persists submission pending and receipt, extracts PDF/PNG/JPG using OpenAI structured output (Zod validated), returns 201 {submission_id,receipt_id,extraction_status}. Extraction failure still persists row, returns extraction_status failed. Persist exact extraction usage in model_calls. Module 1 may insert model_calls for extraction. This is the sole extraction stage.
- POST /api/reconcile JSON {submission_ids:string[]} (1..50): Module 2 returns {results:[{submission_id,run_id:string|null,status,error?:string}]}. Status is approved|flagged|needs_review|pending|rejected; errors must not be reported as approvals. Bounded processing/concurrency. Missing extraction -> needs_review; do not approve partial evidence. Module 1 never calls this automatically.
- POST /api/corrections JSON {submission_id,decision_id?:string,human_verdict:approved|rejected,human_note,correction_type:decision_override|vendor_alias,correction_payload_json:object}. Module 2 returns {correction_id,status}. Atomically persist correction and human result/status, preserving prior decisions; serialize against active reconciliation so a stale run cannot overwrite reviewer action.
- GET /api/reviews returns {submissions:ReviewRow[],summary:{approved_amount_minor,flag_rate,top_flag_reasons:[{reason,count}]},demo_mode:boolean}. ReviewRow={submission fields above,receipt:{id,file_type,extraction_status,parsed_fields_json}|null,decisions:DecisionSummary[]}. DecisionSummary={id,field_checked,check_method,verdict,answer_json,probability,confidence_score,rationale_text,evidence_json}. Decisions are from latest completed run plus applicable human override. flag_rate=(flagged+needs_review)/all reviewed submissions, excluding pending. Approved amounts mean approved, not paid.
- GET /api/receipts/[id] streams authorized-by-demo-scope file or redirects to short-lived signed storage URL. Module 1 owns this. No real user receipts permitted in demo.

## Core behavior

Code computes money comparison, cap and date checks. Elasticsearch retrieves prior duplicate candidates and relevant alias corrections; pass actual evidence records, not only search scores, to Jev. Exclude current submission. Jev handles narrow semantic merchant/name/duplicate judgments with explicit unknown cases. Compute overall status in code after questions return; questions in one Jev call cannot consume one another's answers. Missing receipt name is not automatically mismatch. Never allow model output to override hard policy failure. Every extraction-ready processed claim gets Jev evaluation; service errors route to needs_review. Store evidence-based rationale (templates acceptable); optional OpenAI rationale only on exceptions, not necessary for MVP. Correction retrieval is mandatory; blind re-run auditor is out of scope.

Provide explicit demo adapters/fixtures when credentials are absent, clearly labeled simulated and never silently presented as live provider output. Live API integrations must actually be implemented; no fabricated benchmark/cost figures. Dashboard may initially use fixtures with the exact contract while core endpoints are developed. Poll GET /api/reviews during runs; Realtime is optional polish.

## Demo and acceptance

One clean claim, one duplicate, one ambiguous merchant case corrected by reviewer, a new related claim that benefits, and a counterexample outside correction scope. Dashboard columns: submitted values, receipt values, review status. Drilldown shows evidence, rationale and probability/confidence with accurate labels. Correcting a row calls API, never writes directly from browser. Reconcile button only calls API. Report approvals, review rate, and reasons.

Each task implements and verifies its module, commits to its isolated branch, and writes MODULE_1_HANDOFF.md / MODULE_2_HANDOFF.md / MODULE_3_HANDOFF.md respectively at repo root, documenting files, tests, required env variable names (no secrets), dependencies, integration limitations, and commit SHA. Do not merge or push without further instruction. Shared files are merged from Module 1 scaffold then Module 2 then Module 3. Do not delete existing code or read/copy local .env secrets into commits/prompts.
